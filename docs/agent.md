# Agent interface — riauth.cli/v1

riAuth is managed through the CLI. It does not require an embedded LLM or MCP server. Server-side permissions apply equally to CLI calls and direct HTTP requests.

## Bootstrap and permissions

A human administrator can grant the permissions needed by [the complete example](../examples/identity.toml). Run these examples from the repository root, where `deployment-private/` is ignored by Git; outside the checkout, use a private operator directory:

Read the current numeric revision with `riauth revision`. Use it and a unique, stable operation key for this creation; repeat both values only when retrying this exact request.

```sh
mkdir -p deployment-private
riauth --if-revision '<revision>' --idempotency-key deployer-create-001 agent create deployer \
  --permission user.read=user/alice --permission user.write=user/alice \
  --permission group.read=group/staff --permission group.write=group/staff \
  --permission group.members=group/staff \
  --permission client.read=client/reports --permission client.write=client/reports \
  --permission client.rotate=client/reports \
  --permission state.read=state/revision \
  --permission audit.read=audit/events \
  --ttl 86400 --out deployment-private/deployer.json
```

The credential is disclosed only in the first successful response and written to the new `--out` file. An HTTP exact retry, or a CLI retry with a new unused `--out` path, returns 409 `credential_already_issued` without a token or a second agent. Reusing the original CLI output path fails locally if the file exists. If the credential file was never written, inspect the agent and rotate its credential using the separate rotation command; do not create another agent to recover the token.

Select the credential with `--agent-file` or `RIAUTH_AGENT_FILE`. Its issuer and expiration are checked locally and by the server. Selecting it never falls back to a human session. Credentials expire after 60 seconds to 30 days. A human administrator can rotate with `riauth --if-revision REVISION --idempotency-key KEY agent rotate deployer --out deployment-private/replacement.json`, using a fresh revision and key for that rotation. Revocation uses `--if-revision REVISION --idempotency-key KEY agent revoke deployer`; get the revision with `riauth revision` and reuse the same key only for an exact retry. Rotation immediately invalidates the previous token and preserves permissions. The serving procedure for a stolen agent token, a client secret, and the neighboring session and signing-key actions is [credential compromise](credential-compromise.md). The standalone client uses the same routes: `riauthctl --server URL agent create ID --permission ACTION=KIND/NAME … --out FILE`, `agent rotate ID --out FILE`, `agent revoke ID` and `agent list`. It reads the revision and generates a key unless `--if-revision` and `--idempotency-key` are given, writes the credential only to a new owner-only file `--agent-file` can read, refuses an existing path before any request, and answers an exact retry with 409 `credential_already_issued` and no second file.

`agent create` accepts optional `--parent USERNAME` (HTTP field `parent`). The parent must already exist and be enabled; an administrator may own an agent. The stored link is that user's id (`parent_user`) and does not change on rotation. The agent row records three things separately: the owner (`parent_user`), the human who approved the permissions (`authorized_by`), and the approved permission list (`permissions`). Ownership grants no session and adds no permission. Disabling or deleting the parent immediately stops new agent authentication and durably revokes owned credentials in the same transaction. This applies to administrative, SCIM, manifest, LDAP/cloud-directory, inbound SSF and scheduled-offboarding transitions. Re-enabling the parent cannot restore revoked credentials; inherited active child credentials in older disabled-user snapshots are revoked on re-enable as well. Omit `--parent` for an unowned agent; its approved list remains its only ceiling. Human administrators create and rotate agents.

`riauth capabilities` enumerates the local artifact's compiled features, actions and resource kinds without opening a database; its `features` list is empty because it cannot establish instance usability. The running server's `GET /api/capabilities` reports `feature_states` and lists only locally usable profiles in `features`. Neither report grants an agent permission. Permissions use an exact `kind/name`, or `*` for every resource of that action. There are no implicit permission hierarchies. `client.write` does not include `client.rotate`. Group creation and membership changes have separate permissions. Agents cannot create administrators, alter existing administrator users, issue agent credentials, or authenticate/consent as end users.

`device.enroll=device/<id>` enrolls, lists, and revokes that Windows device. `device.enroll=*` covers every device id. Agents cannot enroll or replace a device for an administrator. The credential provider package is not part of this service; see [enterprise/ENT-13.md](enterprise/ENT-13.md).
`directory.read` and `directory.sync` authorize LDAP on `directory/<id>`. The same actions authorize Google Workspace on `workspace/<id>` and Microsoft Entra ID on `entra/<id>`. A resource of `*` matches every directory resource for that action, including cloud directories. See [Workspace](enterprise/ENT-03.md) and [Entra](enterprise/ENT-04.md).

Additional scoped enterprise actions are:

| Action/resource | Purpose |
| --- | --- |
| `mtls.read=user/<username>`, `mtls.bind=user/<username>` | Inspect or change HTTPS client-certificate bindings; separate from RADIUS `certificate.read` / `certificate.write`. |
| `user.offboard=user/<username>` | Schedule, inspect, reschedule or cancel offboarding. Per-target SCIM deactivation details also need `provisioner.read` on that target. The aggregate diagnostic still withholds this username without this permission. |
| `ssf.configure=ssf/<id>` or `ssf.configure=*` | Read or change an owned outbound Shared Signals stream; `*` permits creation with a generated ID. |
| `ssf.manage=ssf/<id>` | Register pinned inbound signing trust or bind approved local subjects for the selected Shared Signals stream. |
| `audit.read=audit/events` | Audit review, audit CSV export and the Events Map; does not grant user CSV access. |
| `user.read=user/<username>` | Include the selected user in user inventory and CSV exports. |

PAM requester and approver actions use human sessions and configured approvers;
agent permissions do not grant a human session. See the [PAM contract](enterprise/ENT-01.md).

Grant `operations.backup=operations/backup` only to a backup custodian: backups contain the **entire instance**, including private signing keys, MFA secrets and credential records. This permission is broader than resource-scoped inventory access. `operations.read=operations/health` allows doctor, `operations.read=operations/metrics` allows metrics, `operations.read=operations/storage` allows the physical allocation read (`GET /api/operations/storage`) and is also what adds the allocation number to the two metrics responses: a grant for exactly `operations/metrics` receives the same metrics as before and no allocation number (a `*` grant also covers `operations/storage` and receives the cached sample), and `operations/storage` alone does not read metrics. See [storage allocation](roadmap/o06-storage-allocation.md). `operations.read=operations/logout` allows outbox inspection, and `operations.read=operations/offboarding` allows the scheduled-offboarding diagnostic and the deactivation-delivery diagnostic. `operations.read=operations/reconciliation` allows the reconciliation-controller failure diagnostic. `operations.read=operations/provisioning` allows the provisioning-job failure diagnostic; each attention row also requires `provisioner.read` on `provisioner/<target>`. The stored error text stays on `GET /api/provisioning/jobs`. See [provisioning job diagnostics](roadmap/o06-provisioning-job-diagnostics.md). The same `operations.read` resource allows the provisioning deactivation aggregate. Each attention row also requires `provisioner.read` on `provisioner/<stored target>` and `user.read` on `user/<current username>`. The aggregate omits the target name and the stored username. A missing account is withheld. `user.offboard` is not the gate for that route. See [provisioning deactivation diagnostics](roadmap/o06-provisioning-deactivation-diagnostics.md). `operations.read=operations/ssf` allows the outbound Shared Signals delivery diagnostic; each attention row also requires `ssf.configure` or `ssf.manage` on `ssf/<stream id>`. The incident procedure is [SSF delivery](ssf-delivery.md). `key.rotate=key/signing` permits signing-key rotation; `session.revoke=session/<id>` permits that session's revocation.

### Owner authority

An owned agent acts with its approved permissions limited to what its owner holds now. The server recomputes this on every credential use, and before delayed work such as scheduled offboarding, provisioning, reconciliation, invitation acceptance and dynamic client registration:

| Owner | What the owner holds |
| --- | --- |
| Full administrator | Everything, so the approved list is the ceiling. Ownership never grants administrator power: every agent restriction below still applies. |
| Delegated human | Their exact live [delegated grants](#delegated-human-administration-m04-first-slice), personal actions on their own account, and `state.read=state/revision`. |
| Ordinary user | Personal actions on their own account, and `state.read=state/revision`. |

Creation refuses, with `400 invalid_request`, a permission outside the parent's current authority. For a parent who is not a full administrator, each permission must also name an exact resource or `self`: `user.read=user/alice` for a help-desk holder of `user/alice`, not `user.read=*`. `*` is accepted only with an administrator parent or without a parent. A wildcard stored before this rule, or approved for an administrator owner who is later demoted, narrows to the owner's exact resources at use. Promoting an owner to administrator revokes their owned agents, as it removes their delegated grants, so a change of role never widens an agent. A later loss of authority, such as removing a grant or demoting an administrator owner, takes effect on the next request and fails queued work. Role-specific writes do not transfer: help-desk `user.support` is not an agent action, and a directory operator's agent can read and plan its connector but cannot apply, because agent directory writes also need `user.write` and `group.members`. `GET /api/me` with an agent credential returns `permissions` (what it holds now), `approved_permissions`, `parent_user` and `authorized_by`. Administrator `agent list` also reports `effective_permissions`. This applies to existing owned agents without migration: an owned agent whose ordinary owner never held its approved management permissions keeps authenticating, but those permissions no longer apply. Reissue it with an administrator owner, or without an owner, if it still needs them.

### Personal actions

These narrow actions manage one account. Each names `user/<username>`, `*`, or `self`, which an owned agent resolves to its owner's account. `self` is valid only for these actions and only with a parent. None of them implies `user.read` or `user.write`.

| Action | Route |
| --- | --- |
| `profile.read` | `GET /api/users/{username}/profile`: username, display name, email and its verified state. |
| `profile.write` | `PATCH /api/users/{username}` with only `display_name`. Email is a recovery channel and stays on `user.write`. Audited as `user.profile_update`. |
| `sessions.read` | `GET /api/users/{username}/sessions` |
| `sessions.revoke` | `DELETE /api/sessions/{id}` for a session of that account. |
| `consents.read` | `GET /api/users/{username}/consents` |
| `consents.revoke` | `DELETE /api/users/{username}/consents/{client_id}`: withdraws consent and revokes that account's outstanding grants for the client. |
| `agents.read` | `GET /api/users/{username}/agents`: owned agents with their effective permissions. |
| `agents.revoke` | `DELETE /api/agents/{id}` for an agent that account owns, including the calling agent itself. When an agent revokes another agent, the audit event adds `target_parent_user`. |

Agents still cannot alter an administrator account through `profile.write`. Writes keep the usual `If-Match` and `Idempotency-Key` requirements for scoped callers.

## Delegated human administration (M04 first slice)

A full human administrator can replace another enabled, non-administrator's low-risk delegated grants with `PUT /api/users/{username}/delegated-grants` using a JSON array. Changes that add, remove or rebind `directory_operator` or `security_administrator` grants require the [M05 reviewed-grant workflow](reviewed-grants.md), including complete revocation with an empty array. `GET` on the same path reads grants. The same routes are available to an administrator's signed-in browser at `/api/admin/users/{username}/delegated-grants` behind the portal read or write guards. A grant is tied to the exact named target and its stable stored ID; `*` and kind-wide scopes are rejected. Committed changes are live on the next management request and are audited with the assigning actor and scopes. A grant holder cannot change grants, even their own.

```json
[
  {"role":"help_desk","scope":"user/alice"},
  {"role":"application_owner","scope":"client/reports"},
  {"role":"directory_operator","scope":"directory/staff"},
  {"role":"auditor","scope":"audit/events"},
  {"role":"security_administrator","scope":"key/signing"}
]
```

`help_desk` may read its selected ordinary account and update its display name, email, enabled state, password, MFA reset, or sessions through the existing user update API. It cannot create an account; change administrator status, attributes, subjects or email verification; update itself; or update an administrator, another delegated person or a configured privileged-access approver. `application_owner` may read its selected client and update its name, redirect URIs, portal presentation, allowed browser origins and post-logout redirect URIs. It cannot create clients, rotate credentials, change sign-in policy, scopes, enabled state or other provider settings. Both roles can read the configuration revision for conditional writes. Their direct HTTP mutations require `If-Match`; the CLI's `--if-revision` sends the same header. Direct user creation and update, group creation and membership, and client creation and update also require an `Idempotency-Key`; local `riauth` commands for these writes require both `--if-revision` and `--idempotency-key`. The existing CLI user and client commands, direct API routes and browser administration routes all call the same server management methods. The browser page has not yet been tailored to hide unsupported controls.

A help-desk or scoped agent password, factor, or recovery-address change marks the target's credentials as exposed to the operator. This includes agent-created or repaired upstream source links, direct user writes, agent-created local passwords, agent-issued or reissued invitations, desired-state credential and recovery changes, SCIM password or recovery-address writes, and agent-managed client certificate sign-in bindings. Administrator promotion and every nonempty delegated grant are refused until the account owner completes a one-use password reset sent to the address verified before the first operator change. That reset revokes sessions, removes enrolled factors and certificate sign-in bindings, and restores the independently verified recovery address; the owner must enroll new factors. Credential and recovery writes to an existing delegated grant holder are refused. An agent-created local account or agent-issued invitation has no prior verified recovery address and needs explicit offline administrator recovery with factor reset before privilege elevation. Offline recovery also clears the account email so its recovery channel can be established again. Passwordless directory sync, SCIM creation without a password, and passwordless desired-state creation without a verified recovery address remain available under existing agent scopes. Ordinary account reset remains an owner-completed flow; an invitation proof sent to an agent-selected mailbox does not establish independent ownership. For routine help, direct the person to the existing account reset flow so they choose the final password themselves.

Accounts created before elevation provenance was recorded have no trustworthy record of who chose a password, recovery address, invitation recipient or client certificate. Existing administrators remain usable. For an older non-administrator, a missing provenance record closes administrator promotion, nonempty human grants and previously stored human grants, even when no operator-exposure marker exists. Reissuing or accepting an old invitation and resetting a password through an old mailbox do not establish provenance. To elevate such an account, stop other riAuth processes and run local `riauth recover-admin USERNAME --reset-mfa`; this replaces the password, removes factors and certificate bindings, clears the old recovery email and records offline recovery in the same audited transaction. Re-establish the recovery address and enroll factors after the account owner is independently verified. New accounts created through the full human administrator's direct, invitation, desired-state, SCIM or passkey-only paths receive provenance at creation. Agent and connector-created accounts remain ineligible for elevation until offline recovery. Restoring an older backup without provenance has the same fail-closed behavior. New operator-exposure rows pin the previously verified recovery address; older rows with an address mismatch cannot authorize remote recovery. The migration cannot infer trustworthy history from old verification flags or certificate rows, and cannot identify an account already promoted before this safeguard; review those administrators' credentials separately.

`directory_operator` reads and reconciles one configured LDAP directory (`directory/<id>`) or, in Platform, one Workspace or Entra directory (`workspace/<id>` or `entra/<id>`). Reconciliation may change only accounts owned by that connector and their configured group memberships; direct user and group APIs remain unavailable. The operator cannot synchronize their own account. A change to the connector configuration invalidates the old grant. Reviewed plans bind the current grant generation and are checked again at apply. `auditor` reads the single audit stream at `audit/events`, including review, CSV and Platform event map routes; it cannot write. `security_administrator` reads and configures one existing signing domain at `key/<id>`; `key/signing` also permits rotation of the primary signing key. It cannot create a new signing domain or manage other domains.

Each role can read the configuration revision. Grant changes, directory writes and key writes record the actor and selected scope. Grant assignment and revocation remain full-administrator operations through the shared API/browser service; privileged changes require distinct author, reviewer and executor. The administration portal provides a Reviewed grants page for this workflow, and `riauth grants` provides remote commands. Other management commands use the same server checks. The remaining browser controls have not yet been tailored to delegated roles, and the standalone `riauthctl` provides `grants`, `group review` and the `client … review` commands. Desired-state plan/apply remains unavailable to delegated humans.

## Desired state

1. Read `riauth --json schema manifest` and `riauth --json capabilities`.
2. Write a JSON or TOML manifest with `api_version = "riauth/v1"`.
3. Run local `validate --file examples/identity.toml`. This checks structure without reading secrets; dependency and permission checks occur during server planning.
4. Run `plan --file examples/identity.toml --out deployment-private/plan.json`. Inspect its redacted changes and `removal_impact`.
5. Run `apply --plan deployment-private/plan.json --non-interactive --json --run-id <run>` using the same agent. Add `--confirm-removals` after reviewing a plan whose `removal_impact.review_required` is true.
6. Use `get`, `inventory`, `explain`, and `audit` to verify the result.

Include global `--agent-file deployment-private/deployer.json` on remote commands, or set its environment equivalent. Authorized automation may execute this workflow unattended; end-user consent remains a separate interaction.

Manifests reconcile named users, groups, clients, upstream sources, explicit source links, configured workflow definitions, immediate delegated role sets (`delegated_grants`), and non-secret administrator SSF streams (`ssf_streams`). A `delegated_grants` entry is the complete immediate role set for that username and uses the same writer as `PUT /api/users/{username}/delegated-grants`. Help-desk, application-owner, and auditor roles can be replaced immediately. An identical directory-operator or security-administrator grant may stay in that set; changing those roles is refused with no write and stays on the reviewed grant workflow. Agents and delegated humans cannot plan or apply these entries. Omission leaves every account's grants unchanged. An `ssf_streams` entry is the non-secret subset of `POST /api/ssf/admin/streams` and uses that create writer plus the subject-binding writer. It carries id, issuer, audience, events_requested, delivery method, endpoint URL, public verification JWKS, and subject usernames. It has no delivery authorization header, private key, or token. Omission leaves every stream, its bindings, and its stored authorization header unchanged. An explicit `subjects` object, including `{}`, replaces that stream's bindings; omitting `subjects` inside a present stream is rejected. Issuer, audience, events, method, endpoint, and public JWKS are immutable after create, and a mismatch writes nothing. Receiver-managed streams stay on the SSF configuration API. Delegated humans cannot plan or apply streams. An agent needs `ssf.manage` on `ssf/<id>` or `*`. Other enterprise records, such as certificate bindings, Windows devices, and offboarding jobs, use their dedicated APIs or configuration. Omitted resources remain unchanged. Membership of an included group is authoritative. Users and clients are disabled with `enabled = false`; absence is not deletion. Client ID/type and existing user ID are immutable. Last-administrator protection is enforced.

Connector definitions are four optional manifest tables with the shape of their `riauth.toml` tables: `directories` (LDAP), `workspace_directories` and `entra_directories` (Platform only; Essentials refuses them with `Google Workspace and Microsoft Entra connector definitions require Platform`), and `scim_targets`. No other kind exists. They are accepted only when the operator has set `connector_secret_dir` in `riauth.toml`; without it planning fails with 400 and no plan is stored. Every file field (`password_file`, `ca_file`, `client_secret_file`, `key_file`, `certificate_file`, `private_key_file`, `token_file`, `refresh_token_file`, and the OAuth equivalents) is a relative name under that directory: parts of ASCII letters, digits, `.`, `_`, and `-`, joined by `/`. An absolute path, `..`, `.`, an empty part, a part ending in a dot, a backslash, a space, a control character, or any non-ASCII character is refused, so no two spellings of a stored name can alias on a case-insensitive file system. No field accepts a secret value. The operator also pins each credential file in `connector_credentials` in `riauth.toml`, a table from the file's name (relative to `connector_secret_dir`) to the origin it may be sent to, or several comma-separated origins. An origin is `scheme://host[:port]` over https, ldaps, or ldap (http only on loopback); scheme and host are case-insensitive and the default port is implied. An HTTPS host is normalized (IDNA, IP literals, a trailing dot). An LDAP host is compared as written, because the client dials it as written: a stored LDAP URL whose host contains percent-encoding or non-ASCII characters is refused, and an LDAP host with a trailing dot or a short IPv4 form does not match a pin for the plain form. A stored definition may name a credential file only if it is pinned, and every endpoint that file, or a token derived from it, is sent to must be among the pinned origins: the LDAP URL for a bind password; the SCIM URL for a static token; both the token URL and the SCIM URL for an OAuth secret or refresh token, because the access token it yields goes to the target; the token endpoint (Google's for a direct key) and the Admin SDK URL for a Workspace broker secret or direct key; the token URL and the Graph URL for an Entra credential. With no pins no stored definition can name a credential, and every connector needs one, so nothing can be stored. The operator provisions the file, pins its origin, and restarts; the administrator manages everything else remotely. A pin names the credential file exactly as the operator wrote it: pinning `Token` does not pin the spelling `token`, which is a different file on a case-sensitive file system, while ownership and bindings treat spellings that differ only in case as one name. The pin is checked at plan, at apply, and at every start, where a missing or changed pin refuses the start and names the same remedies as any other stored-row failure. The pins are inert while `connector_secret_dir` is unset, so unsetting the directory always lets the process start, but they are still checked for syntax when `riauth.toml` loads. Definitions in `riauth.toml` are not subject to pins. Plan, apply, export, and audit never read those files and never contain their bytes; the operator creates and replaces them, and the CLIs never read or upload them (`secret_references` stays empty). `connector_secret_dir` must be a dedicated directory: it may not equal, contain, or lie inside the data directory, and it may not contain any other configured credential or key file: the database key, TLS keys and certificates, PostgreSQL, mail, signer, controller credential, alert-webhook, device-trust, client-certificate, and LDAP, proxy, and RADIUS listener files (including NAS shared secrets and EAP-TLS keys). Paths from `riauth.toml` and from stored names are compared as absolute, normalized, case-folded paths without reading the file system, so a relative `riauth.toml` path meets an absolute `connector_secret_dir`; a symbolic or hard link inside the directory is not detected. One credential file may belong to one connector only, counting `riauth.toml` and stored definitions together, and names that differ only in case are one name; a shared CA or public certificate file is not a credential, and its name may not be one that is, or may become, a credential (owned by another definition, bound, or pinned). The refusal does not name another connector. Each credential file name also stays bound, permanently, to the destination and identity of the first definition that names it: for LDAP the URL, transport, CA, and bind DN; for SCIM the URL, CA, and the OAuth token URL, CA, client id, audience, and grant; for Workspace the token URL, directory URL, customer id, domain, client id, and delegated user; for Entra the token URL, Graph URL, tenant, and client id. A definition with a different destination or identity cannot name a bound file, even after the connector that first named it has moved to another file, and the plan is refused with 409; provision a new file name instead. Plan and apply never remove a binding, and a restore keeps the bindings of the snapshot it restores. Bindings are rechecked against every stored row at each start, and a row that disagrees with one refuses the start. The operator's pins are the guard that does not depend on the store. Pins are origin-level: the identity fields of a definition (the LDAP bind DN; the OAuth client id and audience; the Entra tenant and client id; the Workspace customer, client id, and delegated user) are chosen by the administrator when a credential file is first claimed and are frozen by its binding afterwards. A refused plan tells whether a file name is pinned, bound, or owned, never a value. An administrator can update a stored row that the operator also copied identically into `riauth.toml`; the copy then differs from the row and refuses the next start with the usual remedies. Retiring an outbound SCIM target stops the deactivation of accounts that were provisioned to it, so deprovision those accounts before retiring it. Changing where a credential is sent also requires new references for every credential file of that connector. Either change, and any change of a file reference or of a scope, is reported as `credential_change`; a scope-only change stays allowed. For a Workspace direct key the groups count as scope, because they bound what its token reads. An id that `riauth.toml` already defines is refused with 409. Only a full human administrator may plan, apply, or export definitions. The `state.apply` and `connector.define` audit rows carry only the kind, id, revision, and digest of a connector change, never a URL, DN, or file name; the administrator's own apply result keeps the full definition. Agents and delegated humans cannot, a workflow review or workflow editor plan that also carries a definition is refused, and a connector change is never eligible for automatic reconcile. Omission leaves every stored definition unchanged. To remove one, list it in `retired_connectors` as `{"kind": "ldap|workspace|entra|scim", "id": "..."}`. The plan shows a `retire` change and counts it as a removal (`removal_impact.retired_connectors`): apply needs the exact plan ID (`X-riAuth-Confirm-Removals`, or `--confirm-removals`), and a retirement is never automatic. Retirement deletes the stored row and keeps every credential binding, so each file name stays bound to its first destination and the id can be defined again only under the binding rule above. It writes a `connector.retire` audit event with kind, id, revision, and digest. Retiring an id that is not stored changes nothing, retiring an id that `riauth.toml` defines is refused with 409, and naming one id as both a definition and a retirement is refused with 400. A retirement needs no `connector_secret_dir`, works on Essentials, and can remove a row that is damaged, so it is the way to clear a stored definition that blocks other connector plans.

Each stored definition has a revision that rises with every change and a digest of its canonical content. Apply returns `activation: "restart_required"` when a plan changed or retired a definition. A stored definition takes effect only when a process starts. `Core::open` copies the rows into that process's configuration, read-only, before any worker or listener starts, and checks the merged configuration with the same rules as `riauth.toml`, including the edition and capability gates and the dedicated-directory and one-owner rules. A running process never reloads them. With `connector_secret_dir` unset, stored rows are neither read nor loaded (dormant); that is the operator's way back to `riauth.toml` alone. An Essentials build still refuses to start on a stored Workspace or Entra row, whatever `connector_secret_dir` says; retire such a row on a Platform build. With it set, a stored row that fails validation, or an id that `riauth.toml` defines differently, refuses the start with a message naming the two remedies: remove the `riauth.toml` entry, or unset `connector_secret_dir`. A `riauth.toml` entry identical to its stored row is a no-op, so reopening an already merged configuration works. `GET /api/state/export` adds a top-level `connectors` object for a full human administrator once a definition is stored or `connector_secret_dir` is set. It carries `connector_secret_dir` (whether this process has it set) and, per definition, `kind`, `id`, `revision`, `digest`, `loaded_in_this_process`, `loaded_revision`, and `restart_required`. A definition that was retired while this process still runs it is listed with `retired: true` and `restart_required: true` until the next start. `riauth export` prints the same object as `connectors` next to `manifest_file`, so a remote administrator can see `restart_required` without a raw API call. The loaded set is per process: on PostgreSQL every process and node must be restarted to load a change, and each reports only its own state. Stored definitions have no reconciliation modes or controllers, because `*_reconciliation_modes` and `reconciliation_controllers` are validated against `riauth.toml` ids; they stay manual review. Replacing the bytes of a file that is already named is read on the next LDAP bind, cloud token request, or SCIM bearer read. `ldap_listeners`, `proxy_listeners`, `radius_listeners`, and `pam_approvers` stay in `riauth.toml` and are rejected as unknown fields.

The restart is an operator step, not part of apply. Write secrets only into owner-only files under `connector_secret_dir`, then stop every riAuth process for that database and start again so each loads the same rows. On PostgreSQL, a stop leaves no other `application_name=riauth` backend. On redb, the database file lock excludes a second server. A restart is accepted by the stored node-security agreement when the issuer, the active capabilities, and the four authentication integers (`access_token_ttl`, `refresh_token_ttl`, `session_ttl`, and `password_history`) are unchanged; stored definitions do not change that agreement. Listen addresses, process role, and credential paths are local and are not part of it. Stored definitions travel with a backup and are kept on restore. A Platform-to-Essentials transition is blocked while a Workspace or Entra definition is stored, and `riauth-maintenance` preflight lists each one; retire them on the Platform build and the blocker clears. Until a leftover row is retired, an Essentials build refuses to start on it and refuses to plan any other definition, and says so. High-privilege directory-operator and security-administrator grant changes stay on the reviewed grant workflow. Receiver-managed SSF streams, delivery authorization, and the delivery lease stay outside the manifest.

Use `password_ref` or `password_hash_ref`, paired with `password_version`, and `secret_ref` paired with `secret_version`. References are `env:NAME` or `file:PATH`; the CLI resolves them on the agent's computer only when applying a credential change. File paths resolve from the CLI working directory; prefer absolute paths. Password hashes must come from an authorized offline export. Client secrets must be 32–1024 bytes. Do not store secrets in user attributes or literal claim mappings: those are public configuration.

An unchanged credential version preserves the existing credential. Changing the version requests rotation. Replanning an already reconciled manifest yields no changes, and applying that plan performs no resource mutations. `export --out deployment-private/current.json` contains visible state and stable IDs but omits credential references/hashes and SSF delivery authorization; add references before using an export to create users or confidential clients on another instance.

A manifest may set `issuer` to the riAuth issuer it was prepared for. Planning and applying then fail unless the instance's issuer is exactly that canonical URL, including any trailing slash. Converted Authentik manifests always set it; `export` never does.

Plans expire after 15 minutes and are bound to issuer, principal, current authority, controller mode, complete plan content and global configuration revision. They record explicit user, client, source and password disables, connector retirements and included-group membership removals. Missing manifest resources are unchanged. Every membership removal, connector retirement or client/source/password disable needs exact plan-ID confirmation; explicit user disables use the shared P03 threshold. The HTTP apply header is `X-riAuth-Confirm-Removals: <exact-plan-id>`. Apply recomputes impact and checks its review binding before reconciling. Applying is one database transaction: failed validation, missing secrets or stale revision commits no resource changes. A repeated successful apply returns its original result to a currently authorized actor, including after loss of the first HTTP response. Applied receipts remain available for roughly one day after plan expiry. The CLI checks applied status before rereading secrets. Unapplied plans created before the review binding was introduced must be replanned.

The optional `state_reconciliation_mode` setting accepts `manual-review`, `guarded-automatic` or `automatic` and controls the server-side `Core::state_reconcile` trigger. Omission stays manual. Guarded automatic stops on every removal. Automatic permits below-threshold explicit user disables, but both modes stop at the shared review floor. Passwordless non-admin user creation and group additions are eligible for automatic apply; other user updates, credential, client, source, source-link, delegated-role, SSF stream, and administrator changes remain review-only. Connector definitions always stop for review; listener and PAM tables are not manifest resources. Automated apply accepts only changes that need no supplied secret. Scheduling and a remote trigger are separate work.

## Direct mutation retries

Prefer plan/apply for batches. User/client/group CRUD, client-secret rotation, signing-key rotation and agent credential management also support persisted idempotency receipts:

```sh
riauth --agent-file deployment-private/deployer.json --json revision
riauth --agent-file deployment-private/deployer.json \
  --if-revision 42 --idempotency-key reports-rotation-20260909 \
  --output-file deployment-private/reports-v2.json client rotate-secret reports
```

Use the actual returned revision. Direct agent mutations require `--if-revision`; its HTTP equivalent is `If-Match: "42"`. Agent create, rotate and revoke require `--idempotency-key` (`Idempotency-Key` over HTTP) as well, including for a human administrator. A stale revision fails. For ordinary receipted mutations, retry the same logical operation with the same key, body and path; the server returns the committed result without rotating again, even though the original revision is now stale. Agent creation and rotation are the exceptions: an exact retry returns 409 `credential_already_issued` without the credential. A different request with that key fails. Authentication and the actor's current authority are checked on replay.

Receipts normally return the original result for 24 hours; agent creation and rotation receipts return only the conflict above, never the credential. Expired receipts reject reuse for another six days, then are cleaned up. Never reuse an operation key for new work. After an uncertain operation outside the receipt window, inspect state before making a new plan. Failed transactions do not reserve the key. End-user login, OAuth exchanges and device approval do not use this mechanism; follow their protocol retry rules.

## Output, secrets and errors

With `--json`, success is:

```json
{"schema_version":"riauth.cli/v1","ok":true,"data":{"changed":true}}
```

Failure is:

```json
{"schema_version":"riauth.cli/v1","ok":false,"error":{"code":"conflict","message":"Configuration revision changed","http_status":409,"retryable":false},"exit_code":5}
```

Remote requests have a 30-second deadline by default, configurable with `--request-timeout SECONDS` or `RIAUTH_REQUEST_TIMEOUT` (1..=86,400), including body receipt. CSV reports write one bounded page at a time and atomically publish the complete private file; `rows` counts logical records, including quoted newlines.

Prompts/progress go to stderr. `--non-interactive` and non-TTY input never prompt. Missing required secrets fail. `schema` exposes JSON Schemas for manifests, plans, apply requests, users, clients, provider settings, agents, Authentik migration input, migration inventories, migration report findings and the CLI envelope. Help/version output remains ordinary CLI text.

| Exit | Meaning |
| --- | --- |
| 0 | Command succeeded; inspect fields such as migration `ready_for_plan` |
| 1 | Operation/local validation failure |
| 2 | CLI syntax/usage error |
| 3 | Authentication failure |
| 4 | Permission denied |
| 5 | Conflict / stale state |
| 6 | Rate limited or temporarily unavailable; bounded retry |

`--output-file` writes the complete result into a new mode-0600 file and returns only its path. Client creation/rotation requires it or explicit `--show-secrets`. Agent create/rotate and recovery-code generation require their own `--out` sink. Existing destinations are rejected. Preserve operation keys when retrying a credential delivery failure, using a new output path. For agent creation or rotation, that exact retry returns 409 without creating the new file or re-disclosing the credential. If the credential file was never written, inspect the agent and begin a separate rotation with a fresh revision and key. OAuth token commands intentionally deliver requested tokens and also support `--output-file`.

## Inventory and explanations

`get client reports`, `get user alice`, and `get group staff` perform exact authorized lookup. `inventory clients --limit 100` returns `items`, `next_cursor` and `revision`; pass the opaque cursor through `--after` until null. Supported collections are users, groups, clients, sources and audit. `get source <id>` performs the corresponding exact source lookup. `--filter` matches resource-name substrings for users, groups, clients and sources. For audit inventory it matches an exact run ID only; the shared `events` resource name is never used as a match. Audit review and `report audit --run-id` also use exact run matching. Cursors are encrypted and bound to principal, collection, filter and revision and expire after one hour. Restart enumeration after a conflict. Lists disclose only permitted resources.

`explain reports alice --scope 'openid profile groups'` requires `client.read=client/reports` and `user.read=user/alice`. It also requires `group.read` for every group consulted by the client's policy and, because this request projects group claims, every group Alice belongs to. The example credential includes `group.read=group/staff` for the example policy; grant read access to any additional memberships before using `explain`. It reports policy reasons and claim previews. `--mfa` simulates an authenticated MFA session; it never creates one. Claims use attributes and bounded declarative mappings, never executable code.

`--run-id` is recorded with authenticated actor, generated request ID and redacted changes. Plan application additionally records its plan ID. Audit is retained for 90 days. `report audit --run-id <run> --out deployment-private/audit.csv` exports an exact automation run; ordinary `audit --limit 100` shows recent events. [Audit review](enterprise/ENT-09.md) exposes exact actor/target/run filters and action prefixes. [CSV reports](enterprise/ENT-15.md) walk every page and write a new private file. Before/after changes cover user, group, client, agent, source and Windows-device records; other event families retain attribution without a universal object diff.

Operational recovery and backup instructions are in [operations.md](operations.md). Configuration changes are atomic locally. Logout delivery is asynchronous, durable and retried; external applications must implement logout-token verification and deduplication.

Plan changes include `secret_references` for only the credentials that will change. The CLI resolves those references for user passwords/hashes, TOTP factors, application secrets and source secrets. Explicit source links and password disabling require no secret value. Unchanged credential versions do not require their files/environment variables to remain available; retrying an applied plan returns its stored result before reading any references. Recreate pending plans produced by an older binary if they lack this metadata for a credential change.

The readers for saved CLI/agent credentials, referenced plan secrets, imported keys, Vault/SMTP/SCIM/cloud-directory/alert credentials and PostgreSQL connection files require bounded regular UTF-8 files with owner-only permissions on Unix (`0600` or `0400`). Validation and reading use the same open descriptor. The CLI reports a missing or invalid private file without printing its contents.

## Policy simulation permissions

The existing `explain` command also requires `group.read=group/<name>` for every group used by the evaluated policy and every actual group projected in its claim preview. `client.read` and `user.read` alone do not expose group membership through explanation. The `simulate` command takes one application, person, requested scope set and assumed assurance, with an optional one-group membership change and configured source. It requires `group.read` for each evaluated policy group and the changed group, plus `source.read=source/<id>` when a source is assumed. It returns a redacted, revision-bound policy decision; it creates no grant, session, token, plan receipt or change audit. Fresh proof and device checks can return `needs_live_proof`. The compact browser form sends the same request through the guarded administration route and the same management service.
