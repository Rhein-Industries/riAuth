# Cloud directory operations

The Platform build exposes the same operational surface for configured Google Workspace and Microsoft Entra directories. Signed-in administrators and delegated directory operators can open **Connectors** under `/admin` for directories they may read; its same-origin routes call the same scoped Core methods and job service.

| Method | Endpoint | Required authority | Behavior |
| --- | --- | --- | --- |
| `GET` | `/api/cloud-directories/{kind}/{id}/operations` | `directory.read` on `{kind}/{id}` | Shows sanitized configuration, mappings, validation, and available reconciliation history. |
| `POST` | `/api/cloud-directories/{kind}/{id}/test-connection` | `directory.sync` on `{kind}/{id}` | Obtains a token and reads one users page without saving a plan or changing accounts. |
| `POST` | `/api/cloud-directories/{kind}/{id}/verify-credential` | `directory.sync` on `{kind}/{id}` | Reopens the configured private file, obtains a token, reads one users page, and records a sanitized last result with audit. Supports `If-Match` and `Idempotency-Key`. |
| `POST` | `/api/cloud-directories/{kind}/{id}/verify-controller` | `directory.sync` on `{kind}/{id}` | Checks the configured reconciliation controller's private agent token against its current scoped authority, records a sanitized readiness result and audit. Supports `If-Match` and `Idempotency-Key`. |
| `PATCH` | `/api/cloud-directories/{kind}/{id}/schedule` | `directory.sync` on `{kind}/{id}` | Enables or disables an existing controller's periodic schedule, or sets its interval to 60–86,400 seconds. Supports `If-Match` and `Idempotency-Key`. |

The browser uses `/api/admin/cloud-directories` to list only readable connectors, plus `/api/admin/cloud-directories/{kind}/{id}/operations`, `/verify-credential`, `/verify-controller`, and `/schedule` for the same read and management actions. The read-only `/test-connection` route remains available. These routes require a signed-in administrator or a delegated directory operator with the exact connector grant, plus the portal request guard. Probe and mutation routes use the browser write guard and call the same scoped Core methods as the bearer API. Verification and schedule changes share their authorization, validation, retry receipts, and audit.

`kind` is `workspace` or `entra`. Configuration validation uses the same structural connector checks as startup and also reports mapped local groups that do not exist. The operations response includes the connector's mapped groups, attributes, username prefix, and reconciliation mode. Its credential status reports only whether the bounded private file can be read with owner-only permissions, its modification time, and that the next token request rereads it. This is a file check, not proof of a valid key, successful rotation, or provider acceptance. The response never includes credential paths, client secrets, private keys, access tokens, or raw scheduler authority, errors, and outcome records.

The optional schedule and ten most recent job summaries come from the existing reconciliation service and appear only when the caller also has its `directory.sync` authority. Before the first scheduler pass, a configured controller is shown as `not_started`. Schedule controls change the persisted periodic cadence; they do not create or edit a controller, credential, or event trigger. Disabling marks queued periodic jobs stale before dispatch; an already running job may finish, and event jobs remain separate. A controller configuration change resets an interval override to its configured interval while retaining a disabled schedule. Removing and later adding the controller creates a new enabled schedule.

Job summaries distinguish pending, running, failed, stale and locally completed outcomes with a fixed vocabulary. Raw job errors and outcomes remain hidden. A `completed` reconciliation job records local controller completion; downstream delivery may still be queued. No schedule or job is synthesized for a connector without a configured controller or history. Controller setup and credential replacement remain server-side operations.

After setting up or rotating a reconciliation controller on the server, select **Verify controller** or call `/verify-controller`. The check rereads the bounded, owner-only agent-token file and requires that the token authenticate as the configured, currently authorized agent for this connector. It does not contact the provider, run a job, or change accounts. The response and saved result contain only `ready` and `checked_at`; the operations view also shows sanitized file readability and modification time. A changed controller configuration hides the previous result, and a restored snapshot clears it. A later file change warrants another check. Readiness is a point-in-time local authority check, not proof that reconciliation will finish successfully. Neither the file path nor token is sent to the browser.

For credential rotation, replace the configured private file on the server with the new credential under the existing owner-only permissions, then select **Verify current credential** in the browser or call `/verify-credential`. The next token request reads the file again. The verification action returns and stores only `connected`, `checked_at`, and a fixed error code and message on failure; it also records a scoped audit event. A repeated idempotency key returns the saved result without making another upstream request once the first request commits. The last result is visible in `operations` after refresh. A restored snapshot clears these results because a restored diagnostic could describe a credential revoked after the snapshot. The browser warns if the file modification time is later than the recorded check. A file timestamp cannot prove which credential a provider accepted, and an operator must not treat a readable file as a successful rotation.

Both connection actions check only token acquisition and the first users response shape. They do not validate group membership pages, the complete directory crawl, local mapping targets, an apply, or downstream account changes. A successful result is an operational reachability check at the recorded time, not permission to skip plan review or evidence of remote account completion. The read-only `/test-connection` probe does not persist connector state or consume the sync retry budget. A verification may repeat its read-only upstream probe if concurrent first attempts use the same key or a process stops before the result is committed; only the committed result and audit are deduplicated.
